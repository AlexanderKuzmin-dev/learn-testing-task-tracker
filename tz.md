# ТЗ: Учебный проект "Task Tracker" для отработки тестирования

## Контекст и цель (важно для исполнителя)

Это учебный проект. **Основная цель — не сам трекер задач, а создание кодовой базы, которую я буду постепенно покрывать тестами (Vitest, React Testing Library, MSW, Playwright) в рамках отдельного обучения.**

Из этого следует:
- **Тесты не нужны** — ни unit, ни e2e, ни конфиги тестовых раннеров. Я добавлю их сам отдельным этапом.
- Функциональность должна быть достаточно разнообразной, чтобы дать материал для разных типов тестов: чистые функции для unit-тестов, интерактивные компоненты для component-тестов, асинхронные запросы для тестов с моками сети, сквозные пользовательские сценарии для e2e.
- Код должен быть чистым и разложенным на отдельные переиспользуемые единицы (утилиты, хуки, компоненты) — не всё в одном файле. Это критично: монолитные компоненты плохо поддаются изолированному тестированию.
- Приоритет — работающая функциональность и понятная структура, а не полировка UI. Стилизация минимальная (можно голый CSS или простейший CSS-modules), без дизайн-систем и анимаций.

## Технический стек

- **React 18+** с функциональными компонентами и хуками
- **TypeScript** в строгом режиме (`strict: true`)
- **Redux Toolkit** — глобальный стейт (не React Context, именно Redux)
- **RTK Query** — все запросы к API строго через него, без ручного fetch/axios
- **Сборщик**: Vite
- **API**: JSONPlaceholder (https://jsonplaceholder.typicode.com) — эндпоинты `/todos`, `/users`

## Функциональные требования

### 1. Загрузка и отображение списка задач
- Получение списка задач с `/todos` через RTK Query (`useGetTodosQuery`)
- Отображение состояний: loading, success, error (с возможностью retry при ошибке)
- Пагинация или ленивая подгрузка (например, по 20 задач с кнопкой "показать ещё") — так как `/todos` отдаёт 200 записей разом, это нужно эмулировать на клиенте

### 2. Фильтрация и поиск (чистая логика, вынесенная отдельно)
- Фильтр по статусу: все / выполненные / невыполненные
- Поиск по тексту задачи (title) с debounce
- Фильтр по пользователю (userId) — подтягивать список пользователей с `/users`
- **Важно**: логику фильтрации/поиска вынести в отдельные чистые функции или selectors, не смешивать с компонентами — это будущий материал для unit-тестов

### 3. CRUD-операции (через RTK Query mutations)
- Добавление новой задачи (форма с валидацией: title обязателен, минимум 3 символа)
- Редактирование задачи inline или в модалке
- Удаление задачи с подтверждением (диалог "точно удалить?")
- Отметка выполнено/не выполнено (optimistic update через RTK Query)

Учитывай, что JSONPlaceholder не сохраняет изменения по-настоящему (отвечает fake-успехом) — реализуй optimistic update в Redux-сторе, чтобы изменения визуально держались в рамках сессии.

### 4. Авторизация (фейковая, для e2e-сценариев)
- Простой экран логина (любой email/пароль, без реальной проверки — валидация только формата)
- Хранение состояния "залогинен" в Redux + persist в localStorage
- Защищённый роут: без логина редирект на /login
- Кнопка логаут

### 5. Детальная страница задачи
- Отдельный роут `/todos/:id`
- Подгрузка данных о пользователе-владельце задачи (связь todo → user через userId)
- Обработка кейса "задачи не существует" (404-состояние)

### 6. Статистика/дашборд (для проверки вычисляемой логики)
- Небольшой блок: сколько всего задач, сколько выполнено, процент выполнения
- Эта логика должна быть чистой функцией/selector'ом, не завязанной на UI напрямую

## Требования к архитектуре кода

- Структура папок: `features/` (по доменам: todos, users, auth), `app/` (store, hooks), `components/` (переиспользуемые UI-элементы: Button, Modal, Input и т.д.)
- Все запросы — через RTK Query `createApi` с чётким разделением на `endpoints`
- Роутинг — react-router-dom
- Формы — можно на голых useState/controlled-инпутах, без сторонних библиотек форм (чтобы не усложнять)
- Типизация: строгие типы для всех сущностей (Todo, User), никаких `any`

## Что явно НЕ нужно делать

- Не подключать Vitest, Jest, RTL, Playwright, MSW и любые тестовые библиотеки
- Не писать ни одного теста
- Не настраивать CI/CD
- Не делать сложный визуальный дизайн — функциональность важнее внешнего вида
